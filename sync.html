sync.WaitGroup e sync.Mutex

O pacote sync traz duas ferramentas que você vai usar o tempo todo com goroutines. O WaitGroup espera um grupo de goroutines terminar, sem chute de time.Sleep. O Mutex deixa só uma goroutine por vez mexer numa variável compartilhada. Nesta aula você vê também uma condição de corrida real, pega pelo detector do Go (-race).

Você vai aprender
  • Esperar goroutines com wg.Add, wg.Done e wg.Wait, e com o atalho wg.Go.
  • O que é uma condição de corrida e como o go run -race a mostra.
  • Proteger uma variável com mu.Lock() e mu.Unlock().
  • O deadlock de um WaitGroup que conta goroutines a mais.
Sobre as saídas. Todas as saídas desta aula foram colhidas rodando o código de verdade, com Go 1.27.3 num Linux (linux/amd64), dentro de ~/projetos/go-nivel3 da usuária fictícia ana, no computador notebook. Em concorrência, a ordem das linhas e os números de uma condição de corrida mudam a cada execução; os endereços de memória (0x00c0…) e os números das goroutines no relatório do -race também. As mensagens do Go aparecem em inglês, exatamente como a ferramenta escreveu: nunca traduzimos nem inventamos saída.

1. WaitGroup: esperar um grupo

O WaitGroup é um contador. Add(1) soma uma tarefa, Done() tira uma, e Wait() espera o contador chegar a zero:

package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	for i := 1; i <= 3; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			fmt.Println("tarefa", i, "pronta")
		}()
	}
	wg.Wait()
	fmt.Println("todas terminaram")
}

Duas execuções:

$ go run .
tarefa 3 pronta
tarefa 2 pronta
tarefa 1 pronta
todas terminaram
$ go run .
tarefa 3 pronta
tarefa 2 pronta
tarefa 1 pronta
todas terminaram

A ordem das tarefas pode mudar, mas todas terminaram sempre vem por último: o Wait() só libera quando as três chamaram Done(). O defer wg.Done() garante o Done mesmo se a função sair no meio.

var wg sync.WaitGroup
o contador, começando em zero. Não precisa de make.
wg.Add(1)
“vou esperar mais uma”. Chame antes do go.
defer wg.Done()
“esta terminou”, no fim da goroutine.
wg.Wait()
espera o contador voltar a zero.

O atalho wg.Go

Desde o Go 1.25, wg.Go(f) faz o Add(1), inicia a goroutine e chama o Done() no fim, tudo de uma vez:

package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	for i := 1; i <= 3; i++ {
		wg.Go(func() {
			fmt.Println("tarefa", i, "pronta")
		})
	}
	wg.Wait()
	fmt.Println("todas terminaram")
}
$ go run .
tarefa 3 pronta
tarefa 1 pronta
tarefa 2 pronta
todas terminaram

2. Condição de corrida

Agora 1000 goroutines somam 1 na mesma variável. O certo seria 1000:

package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	contador := 0
	for i := 0; i < 1000; i++ {
		wg.Go(func() {
			contador++
		})
	}
	wg.Wait()
	fmt.Println("contador:", contador)
}

Três execuções, três resultados errados e diferentes:

$ go run .
contador: 938
$ go run .
contador: 993
$ go run .
contador: 959

O contador++ parece uma coisa só, mas são três passos: ler o valor, somar 1, gravar. Duas goroutines podem ler o mesmo valor ao mesmo tempo, e uma soma se perde. Isso é uma condição de corrida (data race). No seu computador os números serão outros (e às vezes pode até dar 1000 por sorte).

Use -race nos testes

O -race deixa o programa mais lento, então não é para produção. Mas vale rodar os testes com ele: go test -race ./.... Ele só acha corridas que acontecem naquela execução, então teste caminhos concorrentes de verdade.

3. Mutex: um de cada vez

Um sync.Mutex é uma tranca. Lock() fecha (se já estiver fechada, espera); Unlock() abre. Entre os dois, só uma goroutine por vez:

package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	var mu sync.Mutex
	contador := 0
	for i := 0; i < 1000; i++ {
		wg.Go(func() {
			mu.Lock()
			contador++
			mu.Unlock()
		})
	}
	wg.Wait()
	fmt.Println("contador:", contador)
}
$ go run .
contador: 1000
$ go run -race .
contador: 1000

Agora dá 1000 sempre, e o -race não reclama de nada.

defer mu.Unlock()

Em funções maiores, escreva mu.Lock() e logo abaixo defer mu.Unlock(). Assim a tranca abre mesmo se a função sair por um return no meio. Esquecer o Unlock trava todo mundo.

Quando dá errado

Add a mais: espera eterna

Aqui o Add(2) promete duas tarefas, mas só uma chama Done(). O Wait() espera para sempre, e o Go derruba o programa:

package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	wg.Add(2)
	go func() {
		defer wg.Done()
		fmt.Println("só uma tarefa")
	}()
	wg.Wait()
}
$ go run .
só uma tarefa

Copiar um Mutex

Um Mutex (ou uma struct que tenha um) não pode ser copiado depois de usado: passe por ponteiro. O go vet avisa quando você copia sem querer.

Resumo

  • WaitGroup espera um grupo de goroutines: Add/Done/Wait, ou wg.Go + Wait.
  • Várias goroutines escrevendo na mesma variável sem proteção é condição de corrida; o -race mostra onde.
  • Mutex deixa uma goroutine por vez: Lock(), mexe, Unlock().
  • Add a mais que Done termina em all goroutines are asleep - deadlock!.
